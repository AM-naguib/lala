# lala UX Operating Guide

> المرجع الإلزامي لتجربة الاستخدام في كل شاشة جديدة أو تعديل على شاشة قائمة.  
> آخر تحديث: 2026-08-22 — Africa/Cairo.

## الهدف

نجعل التاجر يعرف دائمًا:

1. هو موجود فين.
2. يقدر يعمل إيه الآن.
3. إزاي يرجع أو ينتقل للمهمة التالية.
4. ماذا حدث بعد أي إجراء.
5. كيف يصلح الخطأ بدون فقدان شغله.

الهدف العملي: **أي مهمة متكررة يجب أن تكون قابلة للاكتشاف والوصول خلال مستويين تنقل بحد أقصى، من غير شاشات يتيمة أو روابط وهمية.**

## طريقة استخدام هذا الفولدر

قبل بدء أي Batch:

1. راجع [هيكل المعلومات والتنقل](01-INFORMATION-ARCHITECTURE.md).
2. عرّف المهمة الأساسية ونقطة الدخول والخروج لكل شاشة.
3. طبّق [Checklist الشاشة](02-SCREEN-CHECKLIST.md).
4. سجّل أي مشكلة أو دين UX في [UX Backlog](03-UX-BACKLOG.md).
5. لا تعتبر الشاشة Delivered إذا فشلت في أي بند P0 من الـChecklist.

## مبادئ UX المعتمدة

### 1. لا توجد شاشة يتيمة

كل شاشة لها مدخل واضح من الـSidebar أو صفحة أم أو Contextual link. لا نعتمد على معرفة الرابط المباشر.

### 2. المكان الحالي واضح

استخدم حالة Active واحدة فقط في التنقل الرئيسي، مع `aria-current="page"`، Breadcrumbs عند العمق، وTabs داخل المجموعة الوظيفية.

### 3. إجراء أساسي واحد

كل شاشة تبرز Primary action واحدة. الإجراءات الأقل تكرارًا توضع في Secondary button أو More actions، ولا نحول الهيدر إلى صف أزرار مزدحم.

### 4. المستوى يعكس نوع المهمة

المستوى الأول مخصص للـModules اليومية المستقلة: Dashboard، Orders، Products. المخزون والتنظيم والمنتجات المميزة Sections داخل Products، بينما Import وTrash أدوات تشغيلية. لا نخلط Module وSection وTool في صف واحد أو Tabs متساوية.

### 5. نفس المهمة لها نفس النمط

نفس الكلمات، مواضع الأزرار، كثافة الجداول، حالات النجاح والخطأ، وسلوك الحذف والاسترجاع عبر كل الشاشات.

### 6. الاسترجاع أهم من التحذير

قبل الإجراء المدمر نعرض Preview لما سيتغير. بعده نوضح هل يمكن التراجع أو الاسترجاع، وما الحالة الناتجة.

### 7. لا يوجد رابط لا يعمل

الميزة غير المبنية إما تُخفى، أو تظهر Disabled بوضوح مع “قريبًا”. لا نستخدم رابطًا يبدو عاملًا ثم لا يفعل شيئًا.

### 8. الحالات جزء من التصميم

Default، Loading، Empty، No results، Validation، Error، Disabled، Success، Destructive confirmation، وBackground processing تُراجع قبل التسليم.

### 9. العربية والإنجليزية متساويتان

نراجع RTL/LTR، النصوص الحقيقية، طول العناوين، line-height العربي، وأرقام Mono داخل الجمل العربية. الترجمة ليست خطوة لاحقة.

### 10. الموبايل ليس نسخة مخفية

كل وجهة رئيسية قابلة للوصول على الموبايل. الجداول تحدد أولويات الأعمدة وتوفر Cards أو horizontal scroll مقصود، وأهداف اللمس مريحة.

### 11. حماية البيانات لا تكسر السياق

Wallet masking يخفي البيانات الحساسة فقط، مع إبقاء رقم الطلب والحالة والإجراءات الآمنة مفهومة. نشرح سبب الإخفاء وطريقة الاستعادة.

### 12. نقيس المهمة وليس جمال الشاشة فقط

المراجعة تسأل: هل وجد التاجر المهمة؟ هل أكملها؟ كم خطأ ارتكب؟ هل فهم النتيجة؟

## بوابة قبول UX

لا يمر أي Batch إلا إذا:

- كل شاشة لها Entry point وExit واضحان.
- التنقل Desktop وMobile يعمل بنفس الهيكل.
- Active state وحالة الصفحة صحيحتان.
- Primary action واضح وغير مزدحم.
- الحالات الحرجة والتعافي موثقان.
- العربية والإنجليزية قابلتان للاستخدام فعليًا.
- لا توجد Dead ends أو Dead links.
- كل بنود P0 في Checklist ناجحة.
